# Ministral 3B·8B·14B SQL-only 축소 파일럿 보고서

## 요약

20~30분 이내 보고서 제출을 우선한다는 요청에 따라 추가 실행을 중단하고,
**세 모델과 Original·Star 모두에서 평가가 끝난 MIMIC-IV 공통 표본 84개**를 고정했다.
모델당 28개이며, 이미 저장된 결과를 분석한 것이다. 새로 84개를 재실행하지 않았다.

| 모델 | IncreQA | AdaptQA |
|---|---:|---:|
| Ministral 3B | **2/14 (14.3%)** | **0/14 (0.0%)** |
| Ministral 8B | **5/14 (35.7%)** | **0/14 (0.0%)** |
| Ministral 14B | **9/14 (64.3%)** | **3/14 (21.4%)** |

이 공통 표본에서는 14B가 가장 많이 해결했다. 그러나 IncreQA의 14B는
Original 6/7에서 Star 3/7로 떨어졌고, Star 대화 7/7에서 Original 전용 이름을
한 번 이상 실제 SQL 참조에 사용했다. **높은 성공률과 원래 스키마 이름 사용은
분리해서 봐야 한다.**

AdaptQA에서는 3B·8B가 모두 실패했고, 14B의 성공 3개는 모두 Star에서 나왔다.
따라서 두 태스크 종류를 합친 점수만으로 스키마 효과를 설명하지 않는다.

**이 결과는 사후 완료분 교집합 분석이다.** 처음 계획한 384개 전체 평가나
SQL-only 192개 전체 평가가 완료된 것이 아니며, 무작위 독립 평가셋의 성능 추정이나
모델 크기만의 인과효과로 해석하지 않는다. k=1이므로 p-value는 보고하지 않는다.

## 1. 표본과 선택 기준

각 태스크 종류에서 원래 태스크 7개를 Original·Star 두 스키마로 평가했다.

`7개 × 2 태스크 종류 × 2 스키마 × 3 모델 = 84개 평가 결과`

| 구분 | 고정한 MIMIC-IV 태스크 ID |
|---|---|
| IncreQA | 54, 66, 83, 84, 92, 94, 112 |
| AdaptQA | 3, 10, 13, 14, 15, 19, 25 |

원래 파일럿은 DB·태스크 종류별 해시로 선정한 8개를 사용했다. 마감 시점에 MIMIC-IV는
세 모델의 Original·Star 결과가 대부분 있었지만 eICU는 진행도가 달랐다.
그래서 **세 모델과 두 스키마에서 저장된 점수가 모두 존재하는 태스크의 교집합**을
태스크 종류별로 선택했다. 성공 여부로 태스크를 고르지 않았다.

다음 두 태스크는 해당 흐름의 두 스키마·세 모델 모두에서 대칭적으로 제외했다.

- IncreQA 87: 14B Star의 `validator_error`로 점수가 없었다.
- AdaptQA 12: 14B Original의 `validator_error`로 점수가 없었다.

이렇게 96개 예정 슬롯에서 12개 슬롯을 제외해 84개를 맞췄다. 제외된 슬롯 중 이미
점수가 있던 10개도 원본에는 남겨뒀다. eICU 결과도 삭제하지 않고 본 분석 밖에 보존했다.
완료 여부가 난도·실행 안정성과 관련될 수 있으므로, 완료분 선택에 따른 편향은 남는다.

선택 기준 시점은 **2026-09-10 00:45:20 UTC**, 분석 입력 고정 시점은 **00:47:58 UTC**다.
14개 논리 태스크의 지시문과 정답 값이 세 모델·두 스키마에서 같음을 독립 검산했다.
스키마에 따라 달라지는 정답 SQL 문자열은 동일성 조건으로 삼지 않았다.

## 4. Star 대화의 스키마 이름 사용

기존 읽기 전용 `naming_audit`로 저장된 SQL을 분석했다. 실제 SQL을 다시 실행하거나
점수를 재계산하지 않았다. Original에만 존재하는 테이블·컬럼 이름과 Star에만 존재하는
이름을 구분했다. 별칭, CTE, 자연어·문자열 값, 공통 이름, 순수 메타데이터 탐색은
Original 전용 물리 참조로 세지 않는다.

아래는 **점수가 있는 Star 대화만**의 결과다. 두 종류의 이름을 모두 쓰는 대화·호출이
있으므로 Original 전용과 Star 전용 수를 더해서 전체라고 해석하면 안 된다.

| 흐름 | 모델 | Original 전용 이름 사용 대화 | 해당 이름을 참조한 SQL / 전체 SQL | Star 전용 이름 사용 대화 |
|---|---|---:|---:|---:|
| IncreQA | 3B | 3/7 | 7/177 | 7/7 |
| IncreQA | 8B | 3/7 | 9/93 | 7/7 |
| IncreQA | 14B | 7/7 | 20/74 | 7/7 |
| AdaptQA | 3B | 3/7 | 6/123 | 7/7 |
| AdaptQA | 8B | 4/7 | 7/69 | 7/7 |
| AdaptQA | 14B | 2/7 | 2/73 | 7/7 |

테이블·컬럼 참조 등장 횟수는 다음과 같다. 한 SQL에 여러 참조가 있으면 각각 센다.

| 흐름 | 모델 | Original 전용 테이블 | Original 전용 컬럼 | Star 전용 테이블 | Star 전용 컬럼 |
|---|---|---:|---:|---:|---:|
| IncreQA | 3B | 2 | 5 | 214 | 522 |
| IncreQA | 8B | 1 | 25 | 134 | 505 |
| IncreQA | 14B | 7 | 67 | 88 | 388 |
| AdaptQA | 3B | 6 | 0 | 155 | 497 |
| AdaptQA | 8B | 3 | 4 | 68 | 317 |
| AdaptQA | 14B | 2 | 0 | 86 | 394 |

IncreQA에서 14B의 높은 성능이 Original 이름 사용의 감소로 이어지지는 않았다.
반면 AdaptQA의 14B는 Original 전용 이름을 사용한 대화가 2/7로 적고 성공이 3/7이다.
이는 흐름별 관측 차이이며, 이름 사용이 성공·실패를 유발했다는 인과 증거는 아니다.

파싱과 참조 해석의 불확실성도 남는다. Star SQL의 파싱 실패 / 참조 해석 미확정 호출은
IncreQA에서 3B **6/17**, 8B **0/6**, 14B **0/3**이고,
AdaptQA에서 각각 **6/10**, **0/1**, **0/5**다.
특히 3B의 낮은 확정 Original 참조 수를 낮은 편향으로 단정하지 않는다.

## 5. 실패·중단·누락의 처리

본 표본의 분석용 사본에는 **141개 시도**가 있다.

- `no_error`: 79개 평가 결과.
- `agent_timeout`: 5개 평가 실패. reward 0으로 분모 84개에 포함했다.
- `user_error`: 57개 null-reward 시도. 평가 분모에는 넣지 않고 원본과 사본에 보존했다.

5개 시간 초과는 모두 3B AdaptQA다: Original 태스크 10·13·25,
Star 태스크 15·25. 시간 초과를 제외하거나 성공률을 보정하지 않았다.

풀툴 3B·8B와 SQL-only 3B에서 SQLite 실행 및 `func_timeout` 취소 처리 정체를
읽기 전용 스택 관찰로 확인했다. 설정된 60초 SQL 제한이 취소를 완료하지 못하고,
동기 `env.step()` 밖에서 확인하는 600초 에이전트 제한도 즉시 개입하지 못했다.
이는 FAISS 검색 정체로 확인된 문제가 아니다. 근본적인 네이티브·인터프리터 원인은
확정하지 않았고, 실험 중 제한시간 구현을 바꾸지 않았다.

풀툴을 중단한 뒤 SQL-only 3B는 완료 45개를 보존해 같은 설정으로 재개했고 46개까지
진행했다. 마감 요청 후에는 남은 SQL-only 실행도 중단했다.

## 결론

마감용 공통 표본에서 **14B는 IncreQA 9/14, AdaptQA 3/14로 가장 높은 성공 수**를 보였다.
그러나 IncreQA에서는 Original·Star 격차와 Original 전용 이름 사용이 함께 나타났다.
3B·8B의 AdaptQA는 모두 0/14여서 세밀한 비교 근거가 부족하다.

이 결과는 후속 실험의 방향을 잡기 위한 작은 대응 파일럿이다.
완료분 선택, MIMIC-IV 한정, k=1, 사용자 대화의 확률성, 실행 정체 및 미공개 서빙 정밀도
때문에 전체 벤치마크 성능이나 순수한 모델 크기 효과로 확대 해석하지 않는다.
